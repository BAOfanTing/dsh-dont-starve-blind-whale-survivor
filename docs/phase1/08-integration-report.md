## 2. 逐场景证据

### 场景 1：移动

```
不同位置数：21
3,-15 → 4,-16 → 4,-13 → 4,-14 → 4,-12 → 6,-11 → … → 28,-11
```

每次都是**格子坐标**（世界坐标 / 4 向下取整），和游戏里走动的方向一致。

### 场景 2：受伤

```
tick 66  血 150/150  位置 25,-12  附近 hostile 数量 3
tick 68  血 150/150  位置 25,-12  附近 hostile 数量 3
tick 69  血  49.9/150 位置 25,-12 附近 hostile 数量 3   ← 一次掉 100 血
```

- 掉血发生在**站着不动**的时候，附近一直有 3 个敌对单位 → 与「被围殴」一致；
- 同一次记录里 `health.percent` 也从 100 变成 33.3，`dead` 仍为 `false`；
- 只有 1 次掉血（之后没有再掉），说明不是持续伤害。

### 场景 3：吃东西

```
tick 24→25   饥饿 55.3 → 64.5 (+9.2)   背包: …浆果x1… ⇒ …（浆果消失）
tick 53→54   饥饿 55.9 → 60.5 (+4.6)   背包: …种子x1 ⇒ （种子消失）
```

- 浆果（`berries`）在游戏里饥饿值 **9.375** → 实机 `+9.2`（采样间隔内还有自然消耗）；
- 种子（`seeds`）饥饿值 **4.6875** → 实机 `+4.6`；
- 两次都是「饥饿上升 + 对应物品从背包消失」，**一一对应**，不是别的原因导致。

### 场景 4：采集

```
tick 40→41  背包 采下的草x3 ⇒ x4        位置 4,-16 → 3,-15   nearby harvestable 5 → 4
tick 52→53  背包 采下的草x4 ⇒ x5        位置 6,-13 → 7,-12   nearby harvestable 7 → 8（走进新区域）
tick 56→57  背包 新增 胡萝卜x1           位置 14,-12 → 14,-10
tick 57→58  背包 采下的草x5 ⇒ x6
tick 60→61  背包 采下的草x6 ⇒ x7
tick 64→65  背包 采下的草x7 ⇒ x8
```

- `tick 40→41` 是最干净的证据：**背包 +1 根草，同时附近 harvestable 从 5 降到 4**（刚被采掉的那丛）；
- 走到新区域时 harvestable 会增加（7→8、10），说明扫描是按当前半径实时算的，不是静态值。

### 场景 5：昼夜 / 天数

```
tick 55   phase: dusk → night   day 2
tick 85   phase: night → day    day 3
阶段集合：dusk, night, day
世界温度：22.8 ~ 30.9（随昼夜起伏）
```

- `day` 由 `cycles + 1` 得出，`cycles` 同时保留原始值（0 基）；
- 温度随昼夜变化的趋势也在数据里（夜间更低）。

### 场景 6：天气（未覆盖，如实记录）

```
天气组合（全时段唯一一种）：rain=false snow=false wet=0
```

秋季本来少雨，本次没有遇到降雨/降雪，所以**没有观测到天气变化**。
字段本身可读（`is_raining / precipitation / precipitation_rate / wetness / is_wet / is_snowing / snow_level / is_snow_covered / is_acid_raining` 都有值），
schema 与单测覆盖了「变化时字段形状不变」，但**数值变化没有实机证据** —— 留到下次下雨/入冬时补测。

## 3. 扫描节奏（证明没有每帧扫）

```
state tick : 81 82 83 84 85 86 87 88 89 90 91 92 93 94
nearby 的 scanned_at_tick : 81 81 83 83 85 85 87 87 89 89 91 91 93 93
```

- state 每 2 秒一条、扫描每 4 秒一次 → 每 2 个周期才重扫一次；
- 中间那条用的就是缓存，`scanned_at_tick` 不动；
- 一次扫描 `scanned 150`、只输出 28 条（每类上限 10 + 总数上限 40 + 日志长度预算）。

## 5. 集成过程中发现并修复的缺陷

| # | 现象 | 根因 | 修复 | 记在哪 |
|---|---|---|---|---|
| 1 | 日志里 63/64 条记录解析失败 | 一行塞了 player+inventory+world+40 实体，超过日志 3.9K 截断点 | 拆成 `state` + `nearby` 两条记录，并加 3500 字符预算裁剪 | M5→M6 |
| 2 | `rt`/`gt` 永远是空 | `TheSim:GetTime()` 不存在，`pcall` 吞了错误 | 改 `GetRealTime()/1000` + `GetTick()` | M4 修正 |
| 3 | 主世界 state 里带 `cave` 段 | worldstate 在两个分片都填了 cave 字段 | 只按 `shard == "caves"` 输出 | M4 修正 |
| 4 | 草/浆果丛被归成 `diggable` | 分类顺序让 `workable(DIG)` 先命中 | `harvestable` 判定提前 | M5 修正 |
| 5 | 南瓜灯被归成 `creature` | 有 health+combat 就判生物 | 排除 `structure` 标签 | M5 修正 |
| 6 | Bridge 快照在 Master/Caves 之间跳 | 两个分片都在发状态，只存了一份 | 按 session 分片存，优先给「有玩家」的 | M7 |
| 7 | 同一 tick 的记录被重复计数 | 日志重读/回填时重复 | 每分片去重集合 | M7 |

## 6. 结论与遗留风险

**结论**：Phase 1 的读取链路（Lua 观察器 → 日志记录 → Bridge → REST）在真实游戏里可用，
5 个场景实测通过、契约 380/380 通过、Bridge 端到端一致。

**遗留风险 / 未覆盖**：

1. **天气变化**：本次没遇到降雨，需在雨天/冬季补测（字段可读，但变化未验证）。
2. **联机多人**：只测了单人本地世界；多人时 `AllPlayers` 有多个、Caves 里也可能有人，快照选择逻辑需要复测。
3. **洞穴内游玩**：`caves` 分片有记录（40 条 state），但玩家一直在主世界，洞穴里的玩家字段未实测。
4. **长时间运行**：只跑了 3 分钟游戏时间；日志长时间增长（几百 MB）时 Bridge 的回填/轮转行为只做了单测。
5. **饥饿/理智的负向变化**只做了趋势观测（未精确对齐游戏计时）。
6. 本阶段**不做任何游戏操作**，所以「动作执行正确性」不在本次范围内。
