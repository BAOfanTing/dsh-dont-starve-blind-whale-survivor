## 3. P2：Lease 有限等待

### 机制

新增 `control.acquireWithWait(ownerType, env, opts)`（**没有改 `acquire()` 本身**）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `maxWaitMs` | **3000 ms** | 总等待上限 |
| `pollMs` | **175 ms** | 轮询间隔（`setTimeout`，不阻塞事件循环） |
| 尝试次数上限 | `ceil(maxWait/poll)+2` | 双保险，时钟异常也不会死循环 |

只对两种**临时**状态等待：`handover_revoking`（本轮刚发起换手）、`handover_pending`（别人已发起，我在等）。
其他原因（`bad_owner` / `unknown_owner_instance` / 环境变了）**立刻返回**。

### 提交边界（最重要的一条）

```
调用方 → acquireWithWait()      ← 等待只发生在这里
      → dispatcher.dispatch()
           ├─ validate()         ← 租约校验
           ├─ 组装 envelope
           └─ bridge.call()      ← ★ 命令在这里才第一次写盘
```

`acquire` 与 `validate` 都在 `bridge.call()` **之前**，失败时不产生任何命令文件
（有测试 `P2-12` 专门断言"超时后目录里没有 cmd 文件"）。

### 安全条件一条没放宽

等待期间每轮都重新 `acquire()`（重读权威文件、重算 env、重跑全部校验），
并且每轮都尝试 `completeHandover(readAck())` —— **ACK 的五条硬条件仍由它自己校验**：
`job_cleared === true`、`lease_id` 必须匹配、`epoch`/`generation`/`runtime_id` 逐项匹配、
`acked_at` 在有效窗口内。超时**只返回真实原因**（`timedOut: true`），绝不把租约判成有效。

### 真机效果

| 指标 | AGENT-01（修复前） | AGENT-01.1（修复后） |
|---|---|---|
| `control_denied` 次数 | **2 次**（revoking + handover_pending） | **0 次** |
| 租约等待 | — | 9 次，合计 **559 ms**（最长 430 ms / 3 次尝试） |
| 因交接浪费的模型调用 | 2 次 | **0 次** |

## 7. Pickup 为什么是 NOT_RUN

模型在 20 次预算内**全部用于移动 + 采浆果**，从未调用 `pickup`。
这不是工具问题（`pickup` 在 STABILITY-01 已真机 5/5 通过），而是模型的取舍：
它把"采浆果"当成了当前最优先的事，燧石（8~14 格外）排在其后。

按任务要求 **NOT_RUN / NOT_OBSERVED**，不伪造。
下次可以把预算放到 30 次，或者把实验世界布置成"附近只有可拾取物、没有浆果丛"，
让模型没有别的选择。

## 12. 建议的下一步

1. **Pickup 闭环**：把实验世界布置成"附近只有可拾取物"（或把预算放宽到 30 次），
   让模型没有更优选项，才能真正验到它会不会用 `pickup`。
2. **`stale_snapshot` 的固有竞争**：模型思考 3~5 秒、快照 2 秒一刷，拿旧帧是必然的。
   可以在工具返回里**明确告诉它"这一帧还剩几秒有效"**（`scan.age_ms` 已有，只是没渲染），
   让它知道"现在该先 get_state"。**这属于信息呈现，不是放宽校验。**
3. **笔记世界标识**：`cluster_id` 目前是 `null`。如果能拿到稳定值（比如存档目录名），
   就可以做"按世界分文件"。这需要先确认 `cluster_id` 为什么是 unavailable —— **单独立项**。
4. 不要因为 §6 的两次 `stale_snapshot` 去加复杂规划器；那是信息时效问题，不是模型能力问题。
